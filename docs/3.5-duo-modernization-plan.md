# Sober Dailies 3.5 — iPhone Duo and Platform Modernization

## Overview

Version 3.5 is planned as a platform-modernization release. It will prepare
Sober Dailies for Apple's foldable iPhone Duo, resizable iPhone experiences,
iPad, and iPhone Mirroring while upgrading the Expo and React Native foundation.

The app should not detect or target the Duo by product name. Layout decisions
should respond to the space currently available to each screen. This allows the
same work to improve compact phones, the Duo's outer and inner displays, iPad,
and resizable windows.

No version numbers, dependencies, or build settings are changed by this plan.
Those changes will be made deliberately during the 3.5 implementation.

## Release goals

- Upgrade Expo, React Native, Expo Router, and related packages to the latest
  mutually compatible stable versions available when 3.5 development begins.
- Keep the project in Expo's managed workflow.
- Adopt the React Native New Architecture required by current Expo releases.
- Make every major screen respond safely to live width and height changes.
- Provide purposeful expanded layouts instead of stretching phone layouts.
- Preserve user state while the device folds, unfolds, rotates, or resizes.
- Maintain current behavior on existing iPhone and Android devices.
- Complete a dedicated TestFlight and Android internal-testing cycle.

## Current baseline

The project currently uses Expo SDK 53, React Native 0.79, Expo Router 5, and
the legacy React Native architecture. The app already has two helpful settings:

- `ios.supportsTablet` is enabled.
- The native orientation setting is `default`, allowing portrait and landscape.

Several screens already use `useWindowDimensions()`, and the Daily Reflection
pager already resnaps when its width changes. These are useful foundations.

The main issues identified during the initial review are:

- `app/_layout.tsx` applies a global portrait lock at runtime.
- `WhatsInsideCarousel`, `HamburgerMenu`, and `OTASnackbar` capture window width
  once at module load instead of responding to later size changes.
- Most main screens remain a single full-width column on large displays.
- The custom floating tab bar does not yet have an expanded navigation mode.
- Reading and chat surfaces need controlled line lengths on wide displays.

## Guiding principles

1. **Design for available space, not a device name.** Use live container or
   window dimensions instead of checking for Duo, iPad, landscape, or a device
   model.
2. **Preserve continuity.** Opening or closing the Duo must not reset navigation,
   typed text, audio playback, reading position, modal state, or selected dates.
3. **Keep compact layouts familiar.** Existing phone layouts should remain
   recognizable unless a change clearly improves them.
4. **Use expanded space intentionally.** Prefer centered readable columns,
   adaptive grids, or list-detail layouts over simply making cards wider.
5. **Upgrade in controlled stages.** Stabilize the platform upgrade before
   layering expanded layouts on top of it.

## Implementation plan

### Phase 1 — Establish the 3.5 upgrade baseline

- Record the current production behavior and critical user flows.
- Review current Expo, React Native, and third-party package release notes.
- Select the latest stable Expo SDK and its supported React Native version.
- Upgrade Expo-managed packages with Expo's compatibility tooling.
- Review each third-party native dependency before upgrading it independently.
- Remove obsolete Metro overrides and patches only after confirming they are no
  longer needed.
- Enable the New Architecture and resolve incompatible packages or config
  plugins.
- Keep `appVersionSource` set to `local` and remain in managed workflow.
- Do not run `expo prebuild` or change build profiles without explicit approval.
- Do not change app version or build numbers until Neal explicitly requests it.

### Phase 2 — Make resizing technically safe

- Remove the global portrait lock while retaining any intentional,
  screen-specific behavior for the PDF reader.
- Replace module-level `Dimensions.get('window')` values with live dimensions.
- Audit timers, animations, pagers, sheets, WebViews, PDFs, and keyboard layouts
  for stale width or height values.
- Confirm safe-area padding updates correctly across all display states.
- Ensure navigation and screen state survive live resize events.
- Avoid layout decisions based only on orientation or `Platform.isPad`.

### Phase 3 — Introduce shared responsive layout rules

- Create a small shared responsive-layout helper or hook.
- Define semantic modes such as `compact`, `medium`, and `expanded` from the
  available width; do not expose model-specific checks to feature screens.
- Add shared maximum widths for reading, forms, chat, and modal content.
- Add consistent wide-screen gutters and spacing tokens.
- Prefer flexible calculations over a large collection of device breakpoints.

Exact thresholds should be chosen through Xcode 27 resize testing rather than
guessed from the Duo's physical screen specifications.

### Phase 4 — Adapt the primary experience

#### Today

- Keep the current stacked layout in compact widths.
- Consider placing the checklist and Daily Reflection preview side by side in
  expanded widths.
- Keep text-heavy content within a comfortable reading width.

#### Tools

- Convert the current cards into an adaptive grid.
- Increase the column count only when cards retain comfortable text and touch
  target sizes.

#### Literature

- Preserve the current bookshelf presentation in compact widths.
- Explore a list-detail or library-reader arrangement in expanded widths.
- Verify PDF and HTML readers across live size changes.

#### Journey

- Keep the entry feed and editor stacked on compact displays.
- Consider showing the entries list beside the selected entry or editor on an
  expanded display.
- Preserve unsaved form text during every layout transition.

#### AI Sponsor chat

- Center the conversation and enforce a readable maximum width.
- Keep the composer attached to the keyboard and safe area while resizing.
- Preserve the active sponsor, conversation, scroll position, and draft.

#### Navigation

- Keep the bottom floating tab bar for compact layouts.
- Evaluate a custom navigation rail/sidebar for expanded layouts.
- If the bottom bar remains, center it and cap its width so controls do not
  spread excessively across the inner display.

### Phase 5 — Adapt secondary and transient surfaces

- Onboarding carousel
- Hamburger menu
- OTA update notification
- Paywall and pass offer screens
- Settings
- Speaker player and downloads
- Meditation timer and completion screens
- Calendar, reading-size, sponsor-switch, birthday, gift, and other sheets
- Alerts, menus, share flows, and system permission prompts

Sheets and dialogs should remain appropriately sized and centered on expanded
displays instead of becoming full-width unless the content benefits from it.

### Phase 6 — Regression and resize testing

Use Xcode 27 Device Hub or resizable previews to drag through narrow, medium,
wide, portrait-like, and landscape-like sizes. Test transitions while each
important interaction is active.

Critical scenarios:

- App launch, onboarding, disclaimer, and subscription gate
- Tab and stack navigation
- Daily Reflection paging and date selection
- Active Sponsor chat with a typed draft and visible keyboard
- Active speaker audio and meditation audio
- PDF and HTML reading position
- Journey and inventory forms with unsaved text
- Open sheets, dialogs, menus, and paywalls
- Light mode, dark mode, and large accessibility text
- Offline use, relaunch, and OTA-update handling
- Existing compact iPhones, iPad, and supported Android sizes
- iPhone Duo outer display, inner display, and repeated fold/unfold transitions

Also verify the platform upgrade areas most likely to regress:

- RevenueCat subscriptions and restoration
- SQLite data and migrations
- Secure storage
- iCloud and Google Drive backup
- Notifications
- Contacts, camera, photos, and location permissions
- Supabase access and authentication-related device identity
- Analytics, feedback, and review prompts
- EAS Update compatibility and runtime version behavior

### Phase 7 — Release validation

- Resolve all high-priority resize and upgrade regressions.
- Run TypeScript and available automated checks.
- Produce fresh iOS and Android development builds.
- Complete focused TestFlight and Android internal testing.
- Verify production build profiles without changing `appVersionSource: local`.
- Update the app and build numbers only when explicitly directed.
- Prepare App Store screenshots or release notes if the expanded layout is part
  of the public 3.5 message.

## Suggested acceptance criteria

Version 3.5 is ready when:

- No major screen clips, overlaps, or leaves unusable empty space at supported
  window sizes.
- Folding, unfolding, rotating, and resizing do not lose user state.
- Reading and chat text retain comfortable line lengths on wide displays.
- Navigation remains reachable and understandable in compact and expanded modes.
- Core audio, purchase, storage, backup, notification, and content flows pass
  regression testing.
- Existing iPhone and Android layouts have not regressed.
- The app builds successfully through the approved managed EAS workflow.
